# Sicherheits- und Korrektheits-Audit: TVPN Pro 0.1.5

Stand: 22. November 2026
Scope: Windows-Dienst `tvpnd`, WFP, Tor/Mullvad, IPC, Tauri-Shell, Downloader, Installer, UI-Texte.
Methode: vollständige Code-Lektüre der sicherheitskritischen Pfade, `just verify`, UI-Check, Playwright-E2E, VM-Installer-Smoke, VM-Stale-Recovery, VM-WFP-Smoke.

Dieses Dokument behauptet **nicht**, alle möglichen Fehler gefunden zu haben. Es listet die bei der Prüfung gefundenen Punkte, mit Evidenz und Fix-Reihenfolge. Ein Punkt ohne VM-Test ist als Code-Analyse markiert.

## Schweregrade

- **Critical**: kann Schutz unbemerkt aushebeln, Identität verraten oder SYSTEM-Rechte erlangen.
- **High**: ernste Sicherheits-, Identitäts- oder Vertrauenslücke; muss vor einem "fertig" behoben werden.
- **Medium**: Funktions-, Persistenz- oder Härtungsfehler mit begrenzter Wirkung.
- **Low**: Defense-in-depth, Komfort, kleinere Korrektheit.

## Getesteter Ist-Stand

- `just verify`: 90 Tests grün, 1 WFP-Test bewusst ignoriert (nur VM), Clippy ohne Warnungen, PowerShell-Parser und Redaktions-Gate grün.
- `just ui-check`: 0 Fehler, 0 Warnungen.
- `just e2e`: 5/5 Playwright-Tests grün.
- VM `installer-smoke.ps1`: Exit 0. Installation, Dienst, `OFF`, Enable bis `DEGRADED`, Firewall scharf, TCP 443 blockiert, Panic `OFF`, Netz zurück, Uninstall.
- VM `stale-recovery-smoke.ps1`: Exit 0. Hard-Kill, Filter bleiben, `RECOVERY`, `recover`, Netz zurück.
- VM `wfp-smoke.ps1`: Exit 0. `armed=8`, `disarmed=0`.
- **Nicht getestet**: ICMP, UDP/DNS, IPv6, VPN-Kette, MAC auf physischer Hardware, Hostname-Neustart, Tor Browser, Code-Signierung.

## Critical

### C-01: WFP-Filter werden beim sauberen Dienstende automatisch entfernt (Fail-open)

Evidenz: `service/net/src/wfp.rs`, `impl Drop for WfpEngine` ruft `disarm()`, wenn `installed` gesetzt ist. Das passiert bei jedem normalen Prozessende, auch bei einem SCM-Stop oder einem Panic-Unwind, nicht nur bei `disable`/`panic`.

Wirkung: Der Dienst kann stoppen, ohne dass der Nutzer "Ausschalten" gedrückt hat. Die Filter verschwinden, das Netz ist offen, die UI zeigt aber keinen Zustand mehr. Das widerspricht "fail-closed" und dem statischen WFP-Design.

Fix: `Drop` darf nur das Engine-Handle schließen, niemals filtern. Filter nur über explizites `disarm()` in `disable`, `panic`, `recover` und `uninstall` entfernen. Beim nächsten Start muss `has_own_filters()` weiterhin `RECOVERY` auslösen.

### C-02: Token-, Owner-SID- und Settings-Dateien sind nicht atomar und nicht durchgehend ACL-geschützt; Owner-SID ist SDDL-Injection

Evidenz:
- `service/tvpnd/src/pipe.rs`, `write_token`: `std::fs::write(path, token)` erstellt die Datei mit geerbter DACL, erst danach `set_dacl`. Fehler beim DACL setzen lassen die Datei mit geerbter DACL zurück.
- `save_owner_sid`: `std::fs::write` ohne DACL, ohne Flush, ohne Atomik.
- `owner_sid()` liest `owner.sid` und setzt den Wert ungeprüft in `format!("(A;;GA;;;{owner})")` ein.
- `service/tvpnd/src/lib.rs`, `save_settings`: `std::fs::write`, Fehler werden ignoriert.
- Verzeichnis `%ProgramData%\TVPN` wird mit `create_dir_all` und geerbter DACL erstellt.

Wirkung: Wenn ein lokaler Benutzer in `%ProgramData%\TVPN` schreiben, löschen oder Hardlinks anlegen kann, sind mehrere Angriffe möglich:
1. `owner.sid` durch eine beliebige SDDL-Zeichenkette ersetzen, z.B. eine SID, die dem Angreifer Zugriff auf Pipe und Token gibt.
2. `session.token` als Hardlink auf eine SYSTEM-Datei legen; der Dienst schreibt beim Start den Token und beschädigt die Zieldatei.
3. Token zwischen `write` und `set_dacl` mitlesen.
4. `settings.json` auf `vpn_enabled=false` ändern.
5. Stromausfall/Hard-Reset hinterlässt leere Dateien; der Dienst startet dann ohne gültigen Token/Owner.

Fix: Ein gemeinsames `secure_write` mit `CreateFileW`, expliziter DACL beim Erstellen, `FILE_FLAG_WRITE_THROUGH`, `FlushFileBuffers`, temp+`MoveFileEx`-Replace. Verzeichnis-DACL explizit setzen: SYSTEM/Administratoren Vollzugriff, Installations-Owner nur Lesen, keine Write-/Delete-Rechte für normale Benutzer. Owner-SID mit `ConvertStringSidToSidW` validieren und bei ungültigem Wert auf `Administrators` oder einen sicheren Fallback gehen.

### C-03: Tor-Permit ist nur app-ID-basiert und wird vor dem VPN gesetzt (S1)

Evidenz: `service/tvpnd/src/backend.rs`, `arm()` ruft `permit_app(tor.exe)` und `permit_app(mullvad.exe)` sofort nach `arm_default_deny()`, bevor `vpn_connect()` läuft. `service/net/src/wfp.rs` dokumentiert selbst: "This is a program allowlist, not an interface allowlist: the interface condition (S1) is still open."

Wirkung: Sobald die Filter scharf sind, darf `tor.exe` über jede Schnittstelle ausgehen. Wenn die VPN-Verbindung fehlt, abbricht oder der Tor-Prozess vor dem VPN startet, geht Tor direkt über die reale IP. Genau das ist die zentrale Identitätslücke.

Fix: Entweder Tor-Permit erst nach verifiziertem VPN und mit Interface-/Quell-IP-Bedingung setzen, oder Tor in einem Netzwerk-Namespace/Adapter isolieren. Ohne Mullvad-Konto ist das nicht verifizierbar. Bis dahin darf die UI keinen VPN-Schutz behaupten.

### C-04: Globaler Loopback-Permit hebt die App-Allowlist aus

Evidenz: `service/net/src/wfp.rs`, `install_in_transaction()` legt einen Permit mit `FWPM_CONDITION_FLAGS = IS_LOOPBACK` ohne App-ID an.

Wirkung: Jede lokale Anwendung darf Loopback erreichen. Damit kann jede Malware:
- den Tor-SOCKS-Port `127.0.0.1:9150` benutzen und Daten über Tor exfiltrieren, obwohl sie nicht auf der Allowlist steht,
- den Tor-Control-Port `127.0.0.1:9051` erreichen (Cookie-Auth begrenzt, aber angreifbar, siehe H-04),
- beliebige lokale Dienste ansprechen.

Die UI behauptet "nur Tor und freigegebene Apps". Das ist falsch.

Fix: Loopback nur für die konkreten App-IDs freigeben, die ihn brauchen (`tvpnd.exe`, `tvpn-pro.exe`, Tor Browser, Downloader) und für den Tor-Port. Dazu eine kombinierte Bedingung App-ID + Loopback + Port verwenden. Das erfordert VM-Tests, weil der Dienst selbst Tor-Control über Loopback spricht.

### C-05: Panic und Watchdog sind während `enable` blockiert

Evidenz: `service/tvpnd/src/pipe.rs`, `serve_connection` hält den `Mutex<Service>` für den gesamten `handle()`-Aufruf. `Service::enable` kann bis zu 180 s auf Tor und 40 s auf Mullvad warten. Der Watchdog-Thread und jeder zweite Pipe-Client warten auf denselben Mutex. Der globale Hotkey ruft `panic_now()` synchron auf.

Wirkung: Während des Einschaltens kann weder die UI noch der Hotkey noch der Watchdog eingreifen. Ein hängendes Tor/Mullvad macht den Not-Aus unbrauchbar.

Fix: Langlaufende Backend-Schritte aus dem Mutex heraus in einen eigenen Thread verlagern und den Zustand über eine Nachrichten-Queue führen; oder einen separaten, minimalen Panic-Kanal mit eigenem WFP-Handle bereitstellen, der ohne den Service-Mutex die Filter entfernt. Zusätzlich Timeouts für alle externen Prozesse.

### C-06: UI zeigt nach Dienstausfall weiter "Geschützt"

Evidenz: `ui/src/lib/mock.svelte.ts`, `startPolling()` fängt Fehler mit `catch {}` und ändert den Zustand nicht. `refreshService()` wirft bei `service_unavailable`; der Poll ignoriert das.

Wirkung: Stirbt `tvpnd`, bleibt die UI auf `READY` und zeigt weiter "Geschützt". Der Nutzer hat keine Anzeige, dass der Dienst weg ist. Das ist eine falsche Sicherheitsanzeige.

Fix: Nach einem erfolgreichen Status mindestens einmal `serviceReachable` verfolgen. Bei Poll-Fehler `FAILCLOSED`/`UNKNOWN` mit Banner "Dienst nicht erreichbar, Firewall-Status unbekannt" anzeigen. Beim ersten Start ohne Dienst weiter `OFF` zeigen.

### C-07: Panic/Disable ignorieren Shutdown-Fehler und melden trotzdem Erfolg

Evidenz: `service/tvpnd/src/lib.rs`, `disable()` und `panic()` rufen `let _ = self.backend.shutdown();`. `RealBackend::shutdown` ignoriert Fehler von `child.kill()`, `child.wait()` und `mullvad.disconnect()`.

Wirkung: Tor kann weiterlaufen, das VPN kann verbunden bleiben, während die Firewall entfernt und `OFF` gemeldet wird. Der Nutzer glaubt, alles sei beendet.

Fix: `shutdown()` muss Fehler zurückgeben. Bei Fehler Filter scharf lassen, `FAILCLOSED`/`RECOVERY` melden und den Fehler an die UI geben. Panic darf niemals "OFF" melden, solange ein Prozess oder Tunnel nicht sauber beendet ist.

### C-08: Uninstall und Dienststop können Filter verwaisen lassen oder das Netz öffnen

Evidenz: `service/tvpnd/src/service.rs`, `uninstall()` stoppt und löscht den Dienst, ruft aber nie `recover`/`disarm`. `installer.nsh` ignoriert den Exitcode von `--install` und `--uninstall`. Ein eigener `tvpn-recover.exe` fehlt.

Wirkung: Uninstall im bewaffneten Zustand kann Filter hinterlassen, die niemand mehr über die UI entfernen kann. Umgekehrt kann der Drop-Effekt (C-01) das Netz öffnen, ohne dass der Nutzer es merkt. Der Installer meldet Erfolg, auch wenn der Dienst nicht startet.

Fix: `uninstall()` öffnet WFP und entfernt ausschließlich die eigenen Filter, bevor der Dienst gelöscht wird; bei Fehler Uninstall abbrechen. NSIS-Hook Exitcodes prüfen und bei Fehler `Abort`/Fehlermeldung. `tvpn-recover.exe` als eigenständiges Werkzeug bauen.

### C-09: Panic-Semantik und UI-Texte widersprechen sich

Evidenz: `panic()` entfernt die Firewall und geht nach `OFF`, das Netz ist danach offen. Die UI zeigt "Panik: Netz getrennt." (`mock.svelte.ts`) und den Button "Jetzt sperren" (`SettingsSheet.svelte`). Der Hotkey ist in den Einstellungen als "Strg + Shift + P" beschriftet, tatsächlich ist es `Ctrl+Alt+Shift+F12`.

Wirkung: Ein Nutzer drückt in der Not "Jetzt sperren" und öffnet damit das Netz. Das ist gefährlich und irreführend.

Fix: Entweder Panic als echten Kill-Switch implementieren (Filter bleiben scharf, Tor/VPN werden beendet, Zustand `FAILCLOSED`, Netz bleibt zu) oder die Texte klar als "Schutz beenden, Netz öffnen" formulieren. Das ist eine Sicherheitsentscheidung, keine reine Textänderung. Hotkey-Label korrigieren.

## High

### H-01: UI behauptet nicht implementierte Identitäts-Schutzmaßnahmen

Evidenz:
- `states.ts` `ARMING`: "Die MAC wird gewechselt." `RealBackend::randomize_mac` ändert nie eine MAC, gibt immer `false` zurück.
- `SettingsSheet.svelte` "Hostname": Badge "Neutral". Der Hostname wird nirgends neutralisiert.
- `SettingsSheet.svelte` "VPN": "Ohne VPN startet Tor nicht." Der Dienst startet Tor auch mit `vpn_enabled=false`.
- `SettingsSheet.svelte` "Portal", "Block-Fallback", "Torrents", "Hash-Abfrage" sind ohne Implementierung.
- `states.ts` `READY`: "Nur Tor und freigegebene Apps kommen raus." Siehe C-04.
- `TEARDOWN`: "Spuren aufräumen." Es gibt keine Aufräumroutine.

Wirkung: Der Nutzer wird über den tatsächlichen Schutz getäuscht. Das verletzt die Projektregel "keine falschen Sicherheitsaussagen".

Fix: Nicht implementierte Funktionen entfernen oder sichtbar als "nicht implementiert" deaktivieren. MAC/Hostname-Texte an den echten Zustand binden (Banner `mac_unsupported`, `hostname_unchanged`). "Geschützt" durch "Tor aktiv" ersetzen, solange die Kette ungeprüft ist.

### H-02: Sitzungs-Zusammenfassung meldet für Tor-only "READY"

Evidenz: `Service::disable` setzt `let reached = if self.reached_ready { "READY" } else { self.state.as_str() };`. `reached_ready` wird auch im Tor-only-Pfad gesetzt. Die UI fällt zusätzlich auf `'READY'` zurück, wenn `state_reached` fehlt.

Wirkung: Die Zusammenfassung sagt "Erreichter Zustand READY", obwohl nur `DEGRADED` erreicht wurde. Das ist eine falsche Statusaussage.

Fix: Den tatsächlichen höchsten Zustand speichern (`Ready` oder `Degraded`) und in der Summary ausgeben. UI-Fallback auf `OFF`/`DEGRADED`, nicht `READY`.

### H-03: `leak_check` prüft nur die Anzahl der Filter und einen booleschen VPN-Status

Evidenz: `RealBackend::leak_check` prüft `filters < 8`, `vpn_required && !connected`, `tor.circuit`. Es prüft nicht:
- ob die Block-/Loopback-/App-Filter die erwarteten Keys und Aktionen haben,
- ob Tor über die VPN-Schnittstelle geht,
- ob DNS, IPv6, ICMP oder Raw-Sockets blockiert sind,
- ob der Tor-Prozess der gestartete ist,
- ob die Standardroute stimmt.

Wirkung: Ein unvollständiger oder manipulierter Filtersatz kann als "Leak-Check bestanden" gelten. Der Name ist irreführend.

Fix: Jeden erwarteten Filter-Key mit Aktion und Bedingungen verifizieren; VPN-Schnittstelle/Quell-IP prüfen; DNS-/IPv6-/ICMP-Tests in die VM-Leak-Matrix aufnehmen; Tor-Control-PID gegen den gestarteten Prozess prüfen.

### H-04: Bestehender Tor-Control-Port wird blind vertraut

Evidenz: `RealBackend::tor_start` ruft zuerst `connect_tor()` auf `127.0.0.1:9051` mit `control_auth_cookie` aus `%ProgramData%\TVPN\tor`. Erst wenn das fehlschlägt, startet es `tor.exe`. Es gibt keine Prüfung, ob der Port von einem eigenen Tor-Prozess stammt.

Wirkung: Ein lokaler Prozess kann Port 9051 belegen und einen gefälschten Control-Port mit einem selbst erzeugten Cookie betreiben. Der Dienst glaubt an Bootstrap 100 und Circuit, obwohl kein Tor läuft. Der Leak-Check besteht, die UI zeigt "geschützt".

Fix: Nur den selbst gestarteten Tor-Prozess akzeptieren, Control-Port zufällig wählen oder über einen geschützten Cookie und PID-Prüfung binden. Cookie-Datei mit restriktiver DACL. Bei bestehendem Port ohne eigene PID: nicht vertrauen, neu starten.

### H-05: Keine Laufzeit-Hash-/Signaturprüfung für Tor und Mullvad

Evidenz: `backend.rs` `preflight` prüft nur `path.exists()`. `arm()` permitet den Pfad. `tools/fetch-tor.ps1` prüft den Hash nur beim Bauen. Es gibt keine Prüfung des installierten `tor.exe`/`mullvad.exe` vor dem Start.

Wirkung: Ein ersetztes Binary im selben Pfad bekommt den WFP-Permit und läuft als SYSTEM. Der Hash-Schutz aus dem Plan ist nur ein Build-Schutz.

Fix: Feste SHA-256-Liste im Dienst; vor `spawn`/`permit` prüfen. Bei Abweichung `FAILCLOSED`. Mullvad-Signatur (Authenticode) prüfen, wenn möglich. Build-Inputs im Release-Workflow ebenfalls hashen.

### H-06: Umgebungsvariablen erlauben Token-Exfiltration und beliebige Service-EXE

Evidenz:
- `pipe.rs`: `TVPN_TOKEN_PATH`, `TVPN_PIPE_NAME`, `TVPN_OWNER_SID`.
- `backend.rs`: `TVPN_TOR_EXE`, `TVPN_MULLVAD_EXE`.
- `ui/src-tauri/src/service.rs`: `TVPN_SERVICE_EXE`, `TVPN_TOKEN_PATH`, `TVPN_PIPE_NAME`.
- `service_install` ist als Tauri-Command für die Webview erreichbar.

Wirkung: Wird die UI mit einer manipulierten Umgebung gestartet, kann sie das echte Token an einen falschen Pipe-Namen senden. `TVPN_SERVICE_EXE` kann bei elevated App-Ausführung eine beliebige EXE starten. Das ist eine lokale Privilegien-/Token-Lücke.

Fix: Alle Overrides nur unter `#[cfg(debug_assertions)]` oder hinter einem Test-Feature. Release nutzt feste Pfade und den festen Pipe-Namen. `service_install` aus der Webview entfernen oder nur nach expliziter Bestätigung und mit festem Pfad erlauben.

### H-07: Downloader folgt Redirects nach der URL-Prüfung

Evidenz: `ui/src-tauri/src/download.rs` validiert die Start-URL mit `tvpn_core::url::validate`, baut dann `reqwest::Client` ohne eigene Redirect-Policy. `reqwest` folgt standardmäßig Redirects.

Wirkung: Ein gültiger HTTPS-Host kann auf `http://127.0.0.1:...`, `http://192.168.x.x` oder einen anderen lokalen Dienst umleiten. Das ist SSRF, Protocol-Downgrade und kann interne Dienste ansprechen.

Fix: `redirect::Policy::custom` mit erneuter Validierung jeder Ziel-URL; nur HTTPS und öffentliche Hosts. Zusätzlich DNS-Auflösung prüfen und private/link-local/loopback-IPs blockieren. Keine Redirects zu HTTP.

### H-08: Download schreibt vor dem Scan direkt in den Download-Ordner

Evidenz: `transfer()` berechnet `destination()` im Downloads-Ordner und ruft `fetch_to_file` direkt dorthin. Erst danach läuft `scan()`. Bei Abbruch/Fehler bleiben partielle Dateien liegen; es gibt keine Größenbegrenzung; `filename_from_url` erlaubt reservierte Gerätenamen wie `CON`.

Wirkung: Eine schädliche Datei liegt während des Scans ausführbar im Download-Ordner. Ein Fehler hinterlässt eine unvollständige Datei mit finalem Namen. Ein riesiger Download füllt die Platte. `CON` kann Windows blockieren.

Fix: In einen Staging-Ordner unter `app_local_data_dir` mit `.part` laden, Größenlimit prüfen, scannen, erst bei sauberem/unklarem Urteil atomar in den Download-Ordner verschieben; bei Fehler löschen. Reservierte Namen ablehnen. `Content-Length` und laufende Bytes begrenzen.

### H-09: Quarantäne ist lesbar und ausführbar

Evidenz: `download.rs` `quarantine()` verschiebt die Datei nach `app_local_data_dir/quarantine/<id>.bin`. Keine ACL-Änderung, keine Verschlüsselung, keine Endungslose/Unlesbarkeits-Behandlung.

Wirkung: Eine als Bedrohung erkannte Datei bleibt für den Benutzer und jede Malware im selben Benutzerkontext lesbar/ausführbar. Die UI/Plan-Aussage "Quarantäne unlesbar" ist falsch.

Fix: DACL auf "nur SYSTEM/Administratoren" setzen oder die Datei mit einem zufälligen Schlüssel verschlüsseln, der im Credential Manager liegt. Mindestens Ausführung entziehen und im UI klar als "isoliert, nicht garantiert unlesbar" bezeichnen.

### H-10: Laufende Downloads werden bei Panic/Disable nicht gestoppt

Evidenz: `mock.svelte.ts` `panic()` und `disable()` senden nur Service-Kommandos und leeren `app.downloads`. Die Tauri-`Downloads`-Map und die laufenden `transfer`-Tasks werden nicht abgebrochen.

Wirkung: Nach "Panic" oder "Ausschalten" laufen Downloads weiter, während die Firewall entfernt wird. Sie können über die echte IP weiterlaufen.

Fix: `Downloads` um `cancel_all()` erweitern; Panic/Disable ruft es vor dem Service-Kommando auf und wartet kurz auf das Ende. Partialdateien löschen.

### H-11: `install.ps1` installiert auch ohne Prüfsumme und ohne Signatur

Evidenz: `install.ps1` warnt nur, wenn `SHA256SUMS.txt` fehlt, und installiert trotzdem. Die Summe kommt aus demselben GitHub-Release; keine Signatur, kein Pin.

Wirkung: Ein kompromittiertes Release oder ein entfernter Summen-Asset kann einen manipulierten Installer einspielen.

Fix: Ohne `SHA256SUMS.txt` abbrechen. Zusätzlich Signaturprüfung des Installers (Authenticode) oder eines signierten Manifestes; bis dahin klar als unsignierte Alpha kennzeichnen. Version pinnen oder mindestens `prerelease` filtern.

### H-12: Installer/Service haben keine Failure-Actions und keinen Recovery-Dienst

Evidenz: `service.rs` `install()` legt `AutoStart` ohne `ServiceRecovery` an. `installer.nsh` ignoriert Exitcodes. Es gibt keinen separaten Watchdog/Recovery-Prozess.

Wirkung: Stirbt `tvpnd` beim Boot oder später, startet es nicht automatisch neu. Filter können je nach Drop-Zustand offen oder zu sein; die UI ist weg. Kein Notfallpfad.

Fix: Service-Recovery-Actions (`sc failure`/API) und `DelayedAutoStart` konfigurieren. Eigenständigen `tvpn-recover.exe` bauen. NSIS-Hook Exitcode prüfen.

### H-13: Uninstall lässt ProgrammData-Daten und Tor-Daten stehen

Evidenz: `service.rs` `uninstall()` löscht nur den Dienst. `%ProgramData%\TVPN` mit `session.token`, `owner.sid`, `settings.json`, `tor\` bleibt.

Wirkung: Nach einer Deinstallation bleiben Token, Owner-SID, Einstellungen und Tor-Daten (inkl. Cookie) auf der Platte. Das ist ein Identitäts-/Forensik-Rest.

Fix: Uninstall entfernt `%ProgramData%\TVPN` nach erfolgreichem `disarm`, oder bietet eine explizite Option "Daten behalten". Tor-Daten und Token sicher löschen.

### H-14: `service_install` ist ein unnötiger Webview-Privilegienpfad

Evidenz: `ui/src-tauri/src/main.rs` registriert `service::service_install`; `service.rs` führt `tvpnd.exe --install` aus. Der Installer erledigt die Installation bereits.

Wirkung: Jede Webview-Injection kann Installation/Update des Dienstes anstoßen. Bei elevated App-Ausführung ist das Codeausführung.

Fix: Command aus der Release-Webview entfernen oder auf eine explizite, lokal bestätigte Erstinstallation beschränken; festen Pfad und Hash prüfen.

### H-15: Mullvad wird auch im Tor-only-Modus freigegeben

Evidenz: `RealBackend::arm()` permitet `mullvad.exe` und `mullvad-daemon.exe` unabhängig von `settings.vpn_enabled`.

Wirkung: Im Tor-only-Modus darf die Mullvad-App weiter ins Netz. Sie kann einen Tunnel aufbauen oder Telemetrie senden, den die UI nicht als VPN-Schutz ausweist. Das ist ein unkontrollierter Pfad.

Fix: Mullvad-Permits nur setzen, wenn `vpn_enabled=true` und die Kette verifiziert ist. Tor-only darf Mullvad nicht permiten.

### H-16: WFP deckt nur ALE-Auth-Schichten ab; ICMP/UDP/DNS sind ungeprüft

Evidenz: `wfp.rs` `LAYERS` sind ausschließlich `ALE_AUTH_CONNECT` und `ALE_AUTH_RECV_ACCEPT` (v4/v6). Der VM-Test prüft nur TCP 443.

Wirkung: ICMP, UDP, DNS oder Raw-Sockets können je nach Windows-Verhalten an der Allowlist vorbeigehen. Das ist nicht bewiesen, aber auch nicht ausgeschlossen; der Leak-Test deckt es nicht ab.

Fix: Zusätzliche Block-Filter auf `OUTBOUND_TRANSPORT`/`INBOUND_TRANSPORT` und ICMP-Fehler-ebenen; Leak-Matrix um ICMP, DNS/UDP, IPv6, Raw-Socket erweitern.

### H-17: `verify()` zählt beliebige eigene Filter, nicht den erwarteten Satz

Evidenz: `verify()` zählt alle 36 möglichen Keys. `leak_check` akzeptiert `filters >= 8`. Acht App-Permits ohne Block/Loopback würden die Zahl erfüllen.

Wirkung: Ein unvollständiger Satz kann als vollständig gelten.

Fix: Erwartete Keys mit Aktion/Bedingungen einzeln prüfen; `verify()` in `verify_expected()` umbauen; Leak-Check auf exakte Keys.

### H-18: `owner.sid` kann nach Crash leer sein; kein Administratoren-Fallback

Evidenz: `owner_sid()` liest die Datei, filtert nur leer. Bei leerer/zeros Datei ist `owner` None; die Pipe-DACL enthält nur SYSTEM und den aktuellen Dienst-SID (SYSTEM). Die UI als Benutzer kann das Token nicht lesen.

Wirkung: Nach Hard-Reset ist die UI dauerhaft ausgesperrt; der Dienst läuft, aber die UI kann ihn nicht bedienen. Der Nutzer muss manuell eingreifen.

Fix: Owner-SID validieren; bei ungültigem Wert `Administrators` (S-1-5-32-544) als Lese-Backup in die DACL aufnehmen oder den Owner aus dem Installationskontext erneut ableiten. Kein stilles Aussperren.

### H-19: Keine Code-Signierung

Evidenz: Release-Assets sind unsigniert; `install.ps1` prüft keine Signatur.

Wirkung: SmartScreen warnt; ein manipulierter Installer ist nicht von einem echten zu unterscheiden, wenn die SHA-Datei mitkompromittiert wird.

Fix: OV/EV-Zertifikat, Signatur des Installers und der EXEs, Timestamping; `install.ps1` prüft die Signatur.

## Medium

### M-01: Settings-Persistenz ignoriert Fehler und ist nicht atomar

`save_settings` verschluckt Fehler, schreibt direkt, kein Flush/Replace. `load_settings` fällt still auf Defaults zurück. Fix: `secure_write` + temp+replace + Fehler an die UI; bei korrupten Settings Banner `settings_corrupt`, aber Default `vpn_enabled=true` (fail-closed).

### M-02: `set_settings` meldet Erfolg, auch wenn Speichern fehlschlägt

`let _ = save_settings(...)` und danach `Response::ok`. Fix: Fehler zurückgeben und den In-Memory-Wert nicht als persistiert darstellen.

### M-03: `status` hardcodet `protect_mode`, `net_mode` und Download-Zähler

`"net_mode": "focus", "protect_mode": "tor_vpn", "downloads": {0,0}`. Im Tor-only-Modus ist `tor_vpn` falsch. Fix: aus Settings/Backend ableiten; Download-Zähler mindestens aus der Shell melden.

### M-04: `enable` ignoriert die Request-Argumente

`args.net_mode` und `args.protect_mode` werden nicht geprüft. Ein Client kann beliebige Werte senden; der Dienst nutzt nur Settings. Fix: Whitelist prüfen und bei Abweichung `E_IPC_BAD_SCHEMA`.

### M-05: Viele Settings sind wirkungslos

`tor_bridges`, `portal_timeout_sec`, `block_fallback`, `mac_mode`, `scanner_hash_lookup`, `clipboard_watch`, `torrent_mode` werden im Backend nicht umgesetzt. Fix: entweder implementieren oder aus UI/Contract entfernen; keine falschen Versprechen.

### M-06: Externe Prozesse ohne Timeout

`MullvadClient::run` nutzt `Command::output()` ohne Timeout. `read_status()` wird bei jedem Status-Poll und doppelt pro Poll aufgerufen. Ein hängendes `mullvad.exe` blockiert den Dienst. Fix: Timeout, Backoff, Status cachen.

### M-07: `shutdown` wartet nicht auf VPN-Disconnect

`mullvad.disconnect()` wird gefeuert, aber nicht auf den Status gewartet. Fix: Mit Timeout auf `Disconnected` warten; bei Timeout Fehler.

### M-08: `download_done` liefert den vollen Pfad an die Webview

Der Pfad enthält den Benutzernamen. Die UI zeigt ihn derzeit nicht, aber die API/Events tun es. Fix: Nur den Dateinamen oder einen relativen Pfad liefern; vollständigen Pfad nur lokal für "Im Explorer öffnen" mit separatem Command.

### M-09: `parseDownloadInput` kann bei kaputter Prozentkodierung werfen

`decodeURIComponent` ohne try/catch. Fix: try/catch, Fallback auf sanitisierten Dateinamen; Test.

### M-10: UI-Einstellungen sind optimistisch

`updateSetting` ändert den lokalen Zustand vor der Service-Bestätigung. Bei Fehler wird erst nach `refreshService` zurückgesetzt. Fix: Erst nach Erfolg übernehmen oder Rollback bei Fehler.

### M-11: Tauri-Debug-Config öffnet Remote-Debugging

`tauri.debug.conf.json` setzt `--remote-debugging-port=9222`. Nur Debug, aber nicht in Release verwenden; besser entfernen oder auf `TAURI_DEBUG` beschränken.

### M-12: CSP ist gut, aber nicht vollständig

`default-src 'self'` fehlt `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`. Fix: ergänzen.

### M-13: NSIS-Hook ignoriert Exitcodes

`ExecWait` ohne `$0`-Prüfung, kein Abbruch bei Service-Installationsfehler. Fix: Exitcode prüfen, Fehlermeldung, `Abort`.

### M-14: `fetch-tor.ps1` prüft keine GPG-Signatur

Nur der hartkodierte SHA. Der SHA schützt gegen Manipulation des Downloads, aber nicht gegen einen falschen Hash im Repo. Fix: Signatur der Tor-`sha256sums-signed-build.txt` prüfen oder Hash aus einer signierten Quelle beziehen.

### M-15: Keine Dependency-/Supply-Chain-Prüfung in CI

Kein `cargo audit`, `cargo deny`, `bun audit`. Actions sind an Tags, nicht an Commit-SHAs gepinnt. Fix: Audit-Schritte und SHA-Pinning.

### M-16: `Downloads`-Map ist unbeschränkt

Beliebige IDs aus der Webview wachsen im Speicher; keine Parallelitätsgrenze. Fix: Limit, feste IDs, Größenlimit.

### M-17: Panic/Hotkey melden Fehler nicht

`let _ = panic_now(...)` im Tray/Hotkey. Bei Servicefehler sieht der Nutzer nichts. Fix: Tray-Benachrichtigung/Log, aber ohne Secrets.

### M-18: IPC-Rate-Limit und Pipe-DoS

`IpcError::RateLimit` ist ungenutzt; ein Client kann die einzige Pipe-Instanz mit einer halben Zeile blockieren. Fix: Lese-Timeout, Rate-Limit, `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`.

### M-19: `ConnectNamedPipe`-Fehler erzeugen eine Busy-Loop

Bei Fehlern außer `ERROR_PIPE_CONNECTED` wird sofort erneut versucht. Fix: Backoff/Schlaf.

### M-20: `diagnostics` enthält Fingerprint-Daten

Plattform, Sprache, Fenstergröße, DPR, Theme. Keine IP/MAC/URL, aber für ein Privacy-Tool zu viel für ein öffentliches Issue. Fix: Optional kürzen oder Warnung "kann das Gerät wiedererkennbar machen".

### M-21: "Beenden" im Tray lässt Dienst und Filter laufen

`app.exit(0)` beendet nur die UI. Der Dienst läuft weiter, Filter bleiben. Das ist fail-closed, aber der Nutzer versteht es nicht. Fix: Hinweis oder bewusstes "Nur UI beenden" labeln.

### M-22: Code-/Doku-Widersprüche

`docs/STATE.md` sagt "MAC-Primitive/Tests stehen", UI sagt "Neutral"; `PLAN.md` sagt "keine falschen Claims". Fix: Doku und UI an einen ehrlichen Zustand angleichen.

## Design-Entscheidungen, die vor dem Fix nötig sind

1. **Panic**: Soll Panic ein echter Kill-Switch sein (Filter bleiben scharf, Tor/VPN aus, `FAILCLOSED`, Netz zu) oder weiter "alles aus, Netz offen"? Das aktuelle Verhalten ist "Netz offen", die UI sagt "Netz getrennt". Ich empfehle Kill-Switch.
2. **VPN-Pflicht**: Soll `enable` ohne verifizierte VPN-Kette komplett verweigern? Dann ist Tor-only nicht mehr möglich. Oder bleibt Tor-only als bewusst degradierter Modus?
3. **Loopback-Allowlist**: Welche App-IDs dürfen Loopback/Tor-Port? Ohne diese Entscheidung bleibt C-04 offen.
4. **MAC/Hostname**: Ohne physische Hardware und Neustart sind beide nicht verifizierbar. Sollen sie aus der UI verschwinden, bis sie echt sind?
5. **Signierung**: Zertifikat vorhanden? Sonst bleibt H-19 offen.

## Abdeckungsgrenzen

- Kein formaler Beweis, kein Fuzzing, kein unabhängiges Audit.
- VPN-Kette nicht testbar ohne Mullvad-Konto/App.
- MAC/Hostname nicht testbar ohne physische Hardware/Neustart.
- ICMP/UDP/DNS/IPv6 nicht in der VM-Leak-Matrix.
- Tor Browser, Portal, Fallback, Torrents, Hash-Abfrage nicht implementiert.
- Keine Code-Signierung, kein SBOM, kein reproduzierbarer Build.
